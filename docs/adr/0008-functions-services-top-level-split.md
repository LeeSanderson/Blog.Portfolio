# `Functions/` and `Services/` as the only top-level folders in a backend project

As `email-subscription`'s backend grew past its first couple of endpoints, the original convention — one subfolder per endpoint, directly under the project root — started mixing two different things in the same folder. `Email/`, for instance, held both `SendEmailFunction` (a queue-triggered entry point) and the outbox/sender abstractions and Resend HTTP client it and other functions depended on; `WeeklyDigest/` held the timer-triggered function alongside the RSS feed reader it called. Nothing in the folder name said which classes were entry points and which were implementation detail.

Each app's backend project now has at most two top-level folders: `Functions/{Feature}/`, one subfolder per `[Function]`-attributed trigger plus its private `Request`/`Response` records (or shared message contract, for queue/timer triggers), and `Services/{Area}/`, everything a function delegates to, grouped by responsibility rather than by whichever function happens to call it — the RSS-reading code the `WeeklyDigest` function calls lives in `Services/BlogFeed/`, not `Services/WeeklyDigest/`. Composition-root files (`{App}Options.cs`, `{App}ServiceCollectionExtensions.cs`) stay at the project root, since they wire up the whole project rather than belonging to one feature or service area.

This is a pattern, not a rule that both folders must exist: `apps/example/`'s `Ping` function has no supporting services, so its backend project only has `Functions/`. Tests mirror the same two-folder split under `tests/`.
